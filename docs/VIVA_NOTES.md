# Viva Notes

## Phase 0

- `CLAUDE.md` is a one-line pointer so every Claude Code session reads `SECUREAUTH_PLAN.md` first. The plan holds the rules, so the code stays consistent across sessions.
- `.gitignore` keeps secrets and generated files out of git: `local.properties` (Maps API key), `keystore.properties`, `*.jks` / `*.keystore` (signing keys), `build/`, `.gradle/`, `.idea/` and APK/AAB files.
- The repo is initialised locally with `git init -b main` and has no remote. Each phase becomes one commit credited to its owner, which is our evidence for individual contribution.
- `docs/CONTRIBUTIONS.md` and `docs/GENAI_USAGE.md` are the audit trails: who built what, and how AI was used and what we checked ourselves.
- `README.md` summarises the app, tech stack and build steps. Running `./gradlew assembleDebug` confirms the project builds before any feature code is added.

**Likely examiner questions**

1. *Why is `local.properties` not committed?* It holds machine-specific paths and the Maps API key. Committing a key to a public repo would let anyone use (and bill) it.
2. *Why one commit per phase?* It gives a readable history and shows who wrote which part, so each member can be asked about their own commits.
3. *Why a CLAUDE.md file?* It tells the AI assistant to follow the project rules (Java/XML only, no OTP libraries), so generated code follows the course and project constraints.

## Phase 1

- `gradle/libs.versions.toml` (the version catalog) lists every dependency and its version in one place; `app/build.gradle.kts` refers to them as `libs.xxx`. Only the course-approved libraries were added, and no OTP library.
- `viewBinding = true` makes Android generate a binding class per layout (`activity_splash.xml` becomes `ActivitySplashBinding`). It gives type-safe access to views, so there is no `findViewById` and no cast errors.
- The theme extends `Theme.Material3.DayNight.NoActionBar`. Colors are named in `values/colors.xml` (light) and redefined in `values-night/colors.xml` (dark); Android picks the right file from the phone's dark-mode setting, so `themes.xml` is written once.
- `BaseActivity` extends `AppCompatActivity` and holds shared behaviour (edge-to-edge drawing, system-bar padding, a Toast helper). Every screen extends it, so the session check and broadcast receivers can be added in one place in later phases.
- `SplashActivity` is the launcher: the manifest's `MAIN` + `LAUNCHER` intent filter is on it. The package folders (`crypto`, `data`, `views`, `io`, `location`, `receiver`) hold only a `package-info.java` for now, to fix the architecture early.

**Likely examiner questions**

1. *What does the version catalog do?* It keeps all library versions in one file, so upgrading a library is a one-line change and modules cannot disagree on versions.
2. *How does dark mode work without a second theme?* The theme refers to color names. `values-night/colors.xml` gives the same names darker or lighter values, and Android loads that file when the system is in dark mode.
3. *Why a BaseActivity?* To avoid repeating shared code. Later it will check the login session and register receivers, so a protected screen cannot forget to do it.

## Phase 2

- `DbHelper` extends `SQLiteOpenHelper`: Android calls `onCreate` once to run the six `CREATE TABLE` statements (plus an index on `audit_log(user_id, ts)`), and `onUpgrade` when `DB_VERSION` increases. It is a singleton built from the application context, so the whole app shares one connection.
- Foreign keys are off by default in SQLite, so `onConfigure` calls `setForeignKeyConstraintsEnabled(true)`. Child tables use `ON DELETE CASCADE`: deleting a user also deletes their TOTP secret, backup codes, logs, devices and sessions, and a row for a non-existent user is rejected.
- Each table has a plain Java model class and one DAO (Data Access Object). The DAO is the only place that contains SQL, so screens just call `userDao.findByUsername(name)`.
- Every query uses `?` placeholders with an argument array (`"username = ?"`, `new String[]{name}`). The value is never glued into the SQL text, so input such as `x' OR '1'='1` is treated as plain text and cannot cause SQL injection.
- Nullable columns need care: `lat`/`lng`/`used_at` are `Double`/`Long` objects and are read with `Cursor.isNull` first, because `getDouble` returns 0.0 for NULL, and 0.0 is a real place on the map. Failed attempts are increased in SQL (`failed_attempts = failed_attempts + 1`) so two quick updates cannot overwrite each other.

**Likely examiner questions**

1. *Why use `?` placeholders instead of building the SQL string?* They keep data separate from SQL, which prevents SQL injection and handles quotes in values automatically.
2. *What happens if you delete a user?* With foreign keys on and `ON DELETE CASCADE`, SQLite also deletes every row in the other five tables that belongs to that user.
3. *How do the tests avoid touching real data?* `new DbHelper(context, null)` creates an in-memory database that is thrown away after each test, so every test starts empty.

## Phase 3

- **Base32** turns bytes into text using 32 safe characters (`A-Z`, `2-7`). Every 5 bytes (40 bits) become 8 characters of 5 bits each. Example: `"f"` is `0x66` = `01100110`; split into 5-bit groups `01100` `110` + `00` padding = 12 and 24 = `M` `Y`. `encode` pushes bytes into a bit buffer and reads 5 bits at a time; `decode` does the reverse. It accepts lower case, spaces and `=`, and throws on any other character.
- **TotpEngine.generate** does: (1) `counter = time / period` (the time step number), (2) write it as 8 big-endian bytes, (3) `HMAC(secret, counter)` using `javax.crypto.Mac`, (4) dynamic truncation, (5) `% 10^digits`, (6) pad with leading zeros. Only the HMAC itself comes from the library; everything else is our code.
- **Dynamic truncation (RFC 4226 section 5.3)** avoids always using the same 4 bytes of the hash: the low 4 bits of the *last* byte give an offset, we read the 4 bytes there, and clear the top bit so the number is positive. Worked example, secret `"12345678901234567890"` at t = 59 s: counter = 59 / 30 = 1. HMAC-SHA1 = `75a48a19 d4cbe100 644e8ac1 397eea74 7a2d33ab` (20 bytes). Last byte `0xab`; `0xab & 0x0f` = `0xb` = offset 11. Bytes 11..14 are `c1 39 7e ea`. Clear the top bit: `0xc1 & 0x7f` = `0x41`, so the number is `0x41397eea` = 1,094,287,082. Then `% 10^6` = **287082**, and `% 10^8` = **94287082**, which is exactly the RFC 6238 value for t = 59 (6 digits is just the last 6 of the 8).
- **verify** checks the current step and the step before and after (about 30 s of clock drift or typing delay). It compares with `MessageDigest.isEqual` (constant time) and does not stop at the first match, so response time does not reveal how close a guess was. Codes two steps away, wrong lengths and null are rejected.
- **buildOtpAuthUri** makes the `otpauth://totp/Issuer:account?secret=...&issuer=...&algorithm=SHA1&digits=6&period=30` link that Google Authenticator reads from a QR. Issuer and account are URL-encoded (space becomes `%20`, `@` becomes `%40`). Secrets come from `SecureRandom` (20 bytes = 160 bits). Tests use the official RFC 6238 table (SHA1 and SHA256, 6 times from 59 s to 20,000,000,000 s); the expected values were also re-computed independently with Python.

**Likely examiner questions**

1. *Why does the code change every 30 seconds but both devices agree?* Both compute `floor(unix time / 30)` and HMAC it with the same secret, so as long as the clocks agree they get the same step number and the same code. Nothing is sent over a network.
2. *Why do you accept the previous and next window?* Phone and server clocks are never perfectly equal, and the user needs a few seconds to type. Accepting +-1 step (about 30 s each way) fixes that while keeping the chance of a lucky guess very small (3 valid codes out of 1,000,000).
3. *What is dynamic truncation and why use it?* The HMAC output is 20 bytes but we need a short number. Taking the last byte's low 4 bits as an offset lets every byte of the hash influence the result, and masking with `0x7FFFFFFF` makes the 31-bit result positive in signed Java.

## Phase 4

- **PasswordHasher** uses PBKDF2 with HMAC-SHA256: 16 random salt bytes, 120,000 repetitions, 256-bit output; hash and salt are stored as Base64. The repetition count makes every guess slow for an attacker who steals the database, and the per-user salt means equal passwords give different hashes and pre-computed tables are useless. `verify` re-derives the hash and compares with `MessageDigest.isEqual` (constant time). Both methods overwrite the `char[]` afterwards (and `PBEKeySpec.clearPassword()`), so the password does not linger in memory. A test checks our output against an independent Python PBKDF2 result.
- **KeystoreHelper** asks the Android Keystore for an AES-256 key named `secureauth_totp_key`, created on first use. The key never leaves the secure hardware or system service: our app only asks it to encrypt or decrypt, so a copy of `secureauth.db` alone does not reveal the TOTP secret.
- **AES-GCM** encrypts and also authenticates, adding a 16-byte tag. A fresh random 12-byte IV is used for each encryption (the Keystore chooses it, and reusing an IV would break GCM). We store ciphertext and IV as Base64. Changing even one bit makes `decrypt` throw, which the instrumented test checks.
- **BackupCodeGenerator** makes 10 codes like `K7QM-X2PD` from `SecureRandom`. The alphabet drops 0, O, 1 and I, which leaves exactly 32 symbols (5 bits each), so every symbol is equally likely: 8 characters = 40 bits per code. The plain code is returned once to show the user; only a salted PBKDF2 hash is kept, so it is checked like a password. `matches` ignores case, spaces and a missing hyphen.
- **Design choices**: we use `java.util.Base64` (API 26+) rather than `android.util.Base64` so the hashing code runs in fast JVM unit tests. Hashing is deliberately slow, so later screens must run it off the UI thread; `KeystoreHelper` methods declare `GeneralSecurityException` so callers must handle a lost or tampered key.

**Likely examiner questions**

1. *Why PBKDF2 and not SHA-256 or MD5?* Plain hashes are very fast, so an attacker can try billions of passwords per second. PBKDF2 repeats the HMAC 120,000 times and uses a salt, which slows each guess and stops pre-computed (rainbow) tables.
2. *Why store the TOTP secret encrypted if it is already in a private app database?* The secret must be recoverable (we need it to compute codes), so it cannot be hashed. Encrypting it with a Keystore key means the key is not in the database or the app's files, so a stolen backup or database file is useless without the device.
3. *What does GCM give you over plain AES?* It also detects tampering: the authentication tag fails if the ciphertext or IV is changed, so we never act on corrupted or forged data. The IV must be unique per encryption, which is why it is stored next to each ciphertext.

## Phase 5

- **Register** validates on the screen (username 3-20 characters, password at least 8, confirm must match) and shows errors inline on each `TextInputLayout`; Toasts are only for short results such as "Account created". Usernames are trimmed and lower-cased, so "Alice" and "alice" are the same account. A strength hint (weak/fair/strong) counts character types and length while the user types; only the 8-character minimum is enforced.
- **Passwords never become a String.** Fields are read into a `char[]`, hashed with `PasswordHasher` (salted PBKDF2) and the array is overwritten with zeros. Only the hash and salt go into `users`. PBKDF2 is slow on purpose, so the work runs on a background thread (`BaseActivity.runInBackground`) and the button shows "Please wait..." instead of freezing the screen.
- **Login** looks the user up, then checks the lock, then the password. Wrong username and wrong password give the same message, and for an unknown username we still hash a dummy password, so neither the text nor the response time tells an attacker which usernames exist.
- **Lockout** (`LockoutManager`): each wrong password adds 1 to `failed_attempts`; the 3rd sets `locked_until = now + 5 minutes`, writes `LOCKED_OUT` and shows an AlertDialog with the time left (m:ss). While locked the password is not even checked, so guessing gets nothing. When the lock has expired the counter restarts at 0. The counters are stored in SQLite, so closing the app does not reset them.
- **Navigation and audit**: Splash "Get started" and Login `Create account` use explicit Intents. Login opens Register with the Activity Result API (`registerForActivityResult`) and gets the new username back to pre-fill. After a correct password it passes `userId` in an explicit Intent to the placeholder `TotpVerifyActivity`. Audit rows written: `REGISTER`, `PASSWORD_OK`, `PASSWORD_FAIL`, `LOCKED_OUT`.

**Likely examiner questions**

1. *Why do you use `char[]` for the password and not `String`?* A `String` is immutable and stays in memory until garbage collected, so it cannot be erased. A `char[]` can be overwritten with zeros right after hashing, which shortens how long the password is exposed.
2. *Why show the same error for a wrong username and a wrong password?* If the messages differed, an attacker could test which usernames exist. We also hash a dummy password for unknown users so the response takes about the same time.
3. *Where is the lockout stored and why?* In the `users` table (`failed_attempts`, `locked_until`). Keeping it in the database means closing and reopening the app does not give the attacker new attempts.

## Phase 6

- **What is in the QR.** The app builds an `otpauth://totp/SecureAuth:alice?secret=BASE32&issuer=SecureAuth&algorithm=SHA1&digits=6&period=30` link (`TotpEngine.buildOtpAuthUri`) and ZXing's `BarcodeEncoder` turns it into a QR bitmap shown in an `ImageView`. Google Authenticator reads the same link, so both apps then compute the same codes. Defaults are SHA-1, 6 digits and 30 s because those are what Google Authenticator expects. A test decodes the QR image the screen really shows and checks it matches the secret on screen.
- **Secret handling.** The secret is 20 random bytes from `SecureRandom`, kept in a `ViewModel` so it survives screen rotation but disappears (and is zeroed) when the screen is left. Under the QR it is shown as Base32 in groups of 4 for typing by hand; "Copy" puts the raw Base32 on the clipboard, marked sensitive so Android 13+ hides it from the clipboard preview.
- **Proof before saving.** "I've scanned it" opens a code box. Only if `TotpEngine.verify` accepts what the user typed (which proves the authenticator really holds the secret) do we encrypt the secret with the Keystore (`KeystoreHelper`, AES-GCM) and store ciphertext + IV in `totp_accounts`. A wrong code writes `ENROLL_VERIFY_FAIL` and saves nothing; success writes `TOTP_ENROLLED`. Saving uses `replaceForUser`, one transaction that deletes the old account and inserts the new one, so re-enrolling can never leave zero or two authenticators.
- **Context menu.** Long-press on the QR opens a context menu (`registerForContextMenu`, `res/menu/context_enroll_qr.xml`): "Copy secret" and "Share QR image". Sharing first shows a warning dialog, because the image *is* the secret.
- **Implicit Intent + FileProvider.** Sharing writes the QR as a PNG in `cache/qr/` and sends `ACTION_SEND` with type `image/png`; the user picks the receiving app. Other apps cannot open our private files, so we hand out a `content://` link through `FileProvider` (configured in `file_paths.xml`, limited to that one folder) with a temporary read permission. The PNG is deleted when the screen closes.

**Likely examiner questions**

1. *Why don't you save the secret as soon as it is generated?* If the user closes the screen without adding it to an authenticator, we would hold a secret nobody can use and could lock the user out. Saving only after a correct code proves both sides have the same secret.
2. *What is an implicit Intent and where do you use one?* An implicit Intent names an action (here `ACTION_SEND` with an image) instead of a specific Activity; Android shows the apps that can handle it. Explicit Intents (like Login to Register) name the exact class.
3. *Why FileProvider instead of passing a file path?* Since Android 7 an app may not expose `file://` paths, and other apps cannot read our private storage anyway. FileProvider creates a temporary `content://` URI that gives the receiving app read access to just that one file.

## Phase 7

- **TotpVerifyActivity** takes the 6-digit code and submits by itself when the last digit is typed (a `TextWatcher` checks the length). The secret is decrypted from the Keystore only for the check and overwritten with zeros straight afterwards. Wrong codes write `TOTP_FAIL`, say how many attempts are left, and the 3rd locks the account for 5 minutes (`LockoutManager`, the same counter as passwords). A correct code writes `TOTP_OK`, resets the counter and opens the next step (explicit Intent). A user who never finished enrolling is sent to the Enroll screen first.
- **Why the counter is reset here and not after the password.** If a correct password cleared the failure counter, anyone who knew the password could log in again and again and get 3 fresh guesses at the 6-digit code each time, which is an unlimited number overall. So `LoginActivity` leaves the counter alone and only a correct TOTP code resets it. A test checks this.
- **CountdownRingView** is a custom `View`: `onMeasure` keeps it square, `onDraw` uses `Canvas.drawOval` for the faint track and `drawArc(oval, -90, 360 * progress)` for the arc (start at 12 o'clock, sweep shrinks as `progress` falls from 1 to 0). `setProgress(float)` clamps and calls `invalidate()`; with 5 seconds or less left it switches from the theme's secondary colour to the error colour. Colours come from theme attributes, so dark mode works.
- **DashboardActivity** uses a `Handler` that runs every second, scheduled just after each full second. Each tick regenerates the code with `TotpEngine.generate`, so the code changes by itself when the 30-second window rolls over, and updates the ring from the milliseconds already elapsed in the window. The decrypted secret is loaded in `onStart` and wiped in `onStop`, so it is not in memory while the app is in the background (a test checks this with reflection). Tapping the code uses an `OnTouchListener` (dims the code while pressed) plus a click listener that copies it (without the space) to the clipboard and shows a Toast. `SwipeRefreshLayout` reloads the account and redraws; the options menu has Login history, Backup codes, Trusted devices, Profile, Settings, Help and Logout.
- **Placeholders to know about.** `BiometricGateActivity` is only a stand-in with a clearly marked temporary button so the Dashboard can be reached before Phase 8; Phase 8 replaces it with BiometricPrompt and sessions. Until then the Dashboard has no session check. Menu items other than Logout just show a "coming in a later phase" Toast, and Logout goes back to Login (session end comes in Phase 8).

**Likely examiner questions**

1. *How does the code change by itself every 30 seconds?* A Handler re-runs every second. Each time it computes `floor(time / 30 s)` and the HMAC for that step; when the step number changes, the code changes. The ring uses how many milliseconds have passed in the current step.
2. *How is the ring drawn?* In `onDraw` with `Canvas.drawArc`: start angle -90 degrees (12 o'clock), sweep angle `360 * progress`, stroke style with round caps. The Activity calls `setProgress` each tick, which calls `invalidate()` so Android redraws the view.
3. *Why do wrong TOTP codes count toward the same lockout as wrong passwords, and why not reset it after the password?* The code has only 1,000,000 possibilities, so unlimited guesses would be dangerous. One shared counter, reset only after the second factor succeeds, means an attacker with the password still gets just 3 tries in total before the 5-minute lock.

## Phase 8

- **BiometricGateActivity** shows the system `BiometricPrompt` asking for a strong biometric (fingerprint) with the screen lock (PIN/pattern/password) as fallback. Before showing it, `BiometricManager.canAuthenticate` tells us if it is possible: if nothing is set up a dialog explains how to add a fingerprint or screen lock (with a button to the system settings screen, an implicit Intent); if the device cannot do it at all we explain that and send the user back to login. We never skip this step, because the handshake must not be bypassable. On Android 9 and 10 the strong+lock combination is not supported by the system, so `BiometricSupport` asks for the weak biometric class there.
- **Results of the prompt.** Success creates the session. Each wrong finger writes `BIOMETRIC_FAIL` and counts toward the same 3-strike lockout (the 3rd closes the prompt and shows the lock dialog). Cancelling goes back to Login. Other errors (hardware busy, device lockout) show a message and a "Try again" button. A flag stops late callbacks, for example a success arriving after the account was locked, from doing anything.
- **SessionManager** (a singleton) creates a random 32-byte token with `SecureRandom`, keeps the raw token only in memory, and stores just its SHA-256 hash with `expires_at = now + auto-lock time` (default 5 minutes) in the `sessions` table. A fast hash is enough here, unlike passwords, because the token is 256 random bits and cannot be guessed; the hash only means a copy of the database contains no usable token. A new login replaces the user's older session and removes expired rows.
- **Protecting screens.** `BaseActivity.enforceSession()` runs in `onCreate` and `onResume` of every screen that returns `requiresSession() == true` (the Dashboard now, more later). It needs the token in memory, unexpired, AND its hash still in the database. If not, the session is ended (`SESSION_EXPIRED` is logged when it simply timed out) and the user goes to Login with the back stack cleared. The Dashboard also checks the clock every second, so a session that runs out while the screen is open logs the user out by itself (seen on the emulator). The Dashboard now takes the user from the session, not from an Intent extra, because an extra could name any user.
- **Logout** forgets the token in memory first, then deletes the database row and writes `LOGOUT` in the background, and opens Login with an empty back stack so Back cannot return to the Dashboard. The whole path password -> TOTP -> biometric -> Dashboard works end to end; a real system prompt was checked on the emulator, and its audit trail reads REGISTER, TOTP_ENROLLED, PASSWORD_OK, TOTP_OK, BIOMETRIC_OK, SESSION_START.

**Likely examiner questions**

1. *Why store only a hash of the session token?* If someone copies the database, a plain token would let them act as the logged-in user. The hash cannot be turned back into the token, and the real token exists only in memory, so it is gone when the app process ends.
2. *Why is a fast SHA-256 fine for the token but PBKDF2 is needed for passwords?* Passwords are chosen by people and can be guessed, so hashing must be slow. The token is 32 random bytes (2^256 possibilities), so guessing it is impossible no matter how fast the hash is.
3. *What if the phone has no fingerprint?* `canAuthenticate` reports it. With a PIN or pattern set, the screen lock is accepted as the fallback. With neither, we show a dialog on how to set one up and do not let the login continue, since skipping the step would break the handshake.

## Phase 9

- **Generating.** "Generate new codes" first shows an AlertDialog warning that the old codes stop working. Then `BackupCodeGenerator` makes 10 codes and hashes each one with PBKDF2 (a few seconds, so it runs in the background), and `BackupCodeDao.replaceForUser` swaps the whole set in ONE database transaction (delete old, insert new, roll back if any insert fails). `BACKUP_CODES_GENERATED` is logged. The screen shows "X of 10 codes remaining" by counting unused rows.
- **Shown once.** The plain codes are never stored, only salted hashes, so they appear once in a dialog that cannot be dismissed by tapping outside. They are held in a `ViewModel`, which survives screen rotation (a rotated Activity would otherwise lose them forever); the ViewModel also runs the generation, so a rotation in the middle cannot discard the result. Tapping Done forgets them.
- **Save and share.** "Save as .txt" uses `ACTION_CREATE_DOCUMENT` through the Activity Result API: the system file picker lets the user choose the place, and `FileExporter.writeText` writes to the Uri it returns through `ContentResolver.openOutputStream`. No storage permission is needed because the user grants access to that one file. "Share" sends the same text with an implicit `ACTION_SEND` intent.
- **Recovery.** On the code screen, "Use a backup code instead" opens a screen with a `RadioGroup`: log in with a code, or set up a new authenticator. Both need an unused code. Every stored code has its own salt, so the typed code is hashed against each unused code until one matches. A match is marked used with `UPDATE ... WHERE used = 0`, which only one attempt can win, so a code can never be spent twice. Success logs `BACKUP_CODE_USED` and resets the lockout counter; a wrong code logs `BACKUP_CODE_FAIL` and counts toward the same 3-strike lock.
- **What each path does.** "Log in" returns to the code screen, which carries on to the biometric step (the code stands in for the 6-digit code, it is not recorded as `TOTP_OK`). "Set up a new authenticator" opens the Enroll screen; the old authenticator is replaced only when the new one is confirmed with a valid code, so backing out leaves the old one working (but the backup code is already spent).

**Likely examiner questions**

1. *Why can you only see the codes once?* Only salted hashes are stored, like passwords, so the app cannot show them again. If the database is stolen, the attacker gets hashes that are slow to crack, not usable codes. The user must save them when they are shown.
2. *What is the Storage Access Framework and why use it?* It is Android's system file picker. The user chooses where the file goes and Android gives the app a Uri to write just that file, so the app needs no storage permission at all, which is both simpler and safer.
3. *How do you stop a backup code being used twice, even by two quick taps?* The database update is `WHERE id = ? AND used = 0` and returns how many rows changed. Only the first attempt changes a row (returns 1); the second returns 0, and we treat that as a failure.

## Phase 10

- **The list.** `LoginHistoryActivity` reads the logged-in user's `audit_log` rows (newest first) on a background thread and shows them in a `ListView` through a `SimpleAdapter`, as the lab requires. Each row is a `Map` with the keys icon, event, time and location; the adapter copies each value into the view whose id sits at the same position in its `to` array (`item_history.xml`). A tick or cross icon comes from the entry's result, the time from `DateFormat`, and the location is `19.0760, 72.8777` or "No location" (a missing value is `null`, not 0, because 0,0 is a real place).
- **The date filter.** "Filter by date" opens one `DatePickerDialog` for the first day, then another for the last day (not before the first, and nothing after today). The picked days become exact times: 00:00:00.000 on the first day and 23:59:59.999 on the last, so the whole last day is included. `AuditLogDao.listForUserBetween` runs the query with `?` placeholders. A "Clear filter" chip appears while a filter is active, and the range survives screen rotation.
- **Export.** Options menu, "Export CSV", opens the system file picker (`ACTION_CREATE_DOCUMENT`, so no storage permission) and writes `audit_log.csv` with a header row `ts,datetime,event,result,lat,lng`. It writes the entries currently shown, so an active date filter exports only that range. Fields with commas, quotes or line breaks are wrapped in quotes with `"` doubled (RFC 4180). Text columns that start with `=`, `+`, `-` or `@` get a leading apostrophe, because Excel would otherwise run them as formulas (CSV injection); numbers are left alone so `-72.8` stays a number.
- **Import.** "Import CSV" opens the file picker (`ACTION_OPEN_DOCUMENT`). A file is untrusted input, so before storing anything we check: size under 2 MB, a header containing `ts` and `event`, the time is a number, the event looks like our own codes (`PASSWORD_OK`), the result likewise, and any coordinates are real numbers in range (and both present). Rows that fail are counted and skipped; a row with the same time and event as one already stored (or earlier in the file) is a duplicate and skipped; the rest are inserted in one transaction, always for the logged-in user. A Toast reports "Imported X, skipped Y duplicates and Z invalid rows".
- **Why a hand-written CSV parser.** It needs to handle commas and line breaks inside quotes, `""` for a quote, CRLF/LF, and a BOM that Excel adds. It is a small state machine (inside quotes or not) with unit tests, including a random round-trip test that writes and reads back 300 sets of awkward text.

**Likely examiner questions**

1. *How does a SimpleAdapter work?* You give it a list of `Map`s, a row layout, the map keys to read (`from`) and the view ids to fill (`to`). For each row it takes `map.get(from[i])` and puts it into the view `to[i]`: text into a TextView, an int resource id into an ImageView. We added a ViewBinder only to set an accessibility description on the icon.
2. *What is CSV injection and how do you stop it?* If a cell starts with `=`, `+`, `-` or `@`, a spreadsheet may treat it as a formula and run it (for example open a link). On export we put an apostrophe in front of such text, and on import we reject any event name that is not a plain upper-case code.
3. *Why does the filter end at 23:59:59.999 and not at the start of the last day?* A date picker gives only a day. If the end were midnight at the start of that day, everything that happened on the last day would be excluded. Using the last millisecond of the day makes the range inclusive.

## Phase 11

- **Asking for location.** The first time you log in, a dialog explains why (record the approximate place of each login, only on the phone, optional) BEFORE Android's own permission dialog appears; "Not now" is fine. After that we never ask again, and without permission the place is simply stored as `NULL` ("no location") and the login still works. `LocationHelper` (in `location/`) checks the permission with `ContextCompat.checkSelfPermission` and asks for the position once with `FusedLocationProviderClient.getCurrentLocation`, giving up after 8 seconds so a slow GPS never blocks a login.
- **Where the place is stored.** The lookup happens when you press Log in (so `PASSWORD_OK` and `PASSWORD_FAIL` get it) and again when the biometric step succeeds (`SESSION_START`). It goes into the `lat` and `lng` columns of `audit_log`. A missing place is `NULL`, never 0, because 0,0 is a real spot in the sea.
- **Suspicious login.** When a login completes, we find the previous `SESSION_START` that has a place, work out the distance with the haversine formula (the great-circle distance on a sphere of radius 6371 km), and if it is MORE than 100 km we write `SUSPICIOUS_LOCATION` (with the new place) and the Dashboard shows an "Unusual login location" warning with a "View map" button. The comparison is made before the new row is written, otherwise the login would be compared with itself. No place now, or no earlier place, means nothing to compare and no warning. Checked on the emulator: Mumbai then Pune gave "about 120 km", matching the computed 120.15 km.
- **The map.** `LoginMapActivity` hosts a `SupportMapFragment`. For every entry with a place it adds a `Marker`: green for successes, red for failures and `SUSPICIOUS_LOCATION`; the info window shows the event as title and the date-time as snippet; `LatLngBounds` moves the camera so all markers are visible (a single marker gets a fixed zoom). It opens from the history screen's options menu or from the warning dialog.
- **The API key.** `app/build.gradle.kts` reads `MAPS_API_KEY` from `local.properties` (never committed) and passes it as a `manifestPlaceholder`, which fills `${MAPS_API_KEY}` in the manifest's `com.google.android.geo.API_KEY` meta-data. Without a key the app still builds and runs, but Google serves no map tiles.

**Likely examiner questions**

1. *Why do you explain before asking for the permission, and what if the user says no?* Android shows its permission dialog only briefly and says nothing about why; our own first dialog explains the benefit in plain words. If the user says no, location is optional: logins work, the place is stored as NULL, and we do not nag again.
2. *How do you work out that two logins are 100 km apart?* With the haversine formula: it turns the difference in latitude and longitude into the angle between the two points as seen from the Earth's centre, and multiplies by the Earth's radius (6371 km). It is accurate to well under 1%, plenty for a 100 km rule, and we compare "greater than 100", not "at least 100".
3. *Why is the Maps key not in the source code?* A key in a public repository can be copied and used (and billed) by anyone. It lives in `local.properties`, which is gitignored, and Gradle injects it into the manifest at build time; the key should also be restricted to Android apps with this package name and the app's signing certificate.

## Phase 12

- **What "trusted device" means here.** At registration, if "Trust this device" is ticked, this phone is added to the `trusted_devices` table (name = `Build.MANUFACTURER` + `Build.MODEL`, for example "Google Pixel 8") and `DEVICE_TRUSTED` is written to the audit log. The Login screen has no check box, so registration is the only place to opt in.
- **Which row is "this phone"?** The table has only a name column, so the name cannot identify the phone (and the user may rename it). `DeviceTrust` therefore saves the row's id in SharedPreferences under `trusted_device_id_<userId>`. Renaming changes the name only; the link survives.
- **The screen.** `TrustedDevicesActivity` shows the rows in a `ListView` filled by a `SimpleAdapter` (icon, name, "Added <date>", "Trusted / Revoked", plus "This device"). A long-press opens a context menu: **Rename** (a dialog with a text box; a blank or over-40-character name keeps the dialog open with an error) and **Revoke** (an `AlertDialog` asks first, then sets `revoked = 1`). Both write an audit row (`DEVICE_RENAMED`, `DEVICE_REVOKED`). A revoked row stays in the list and only offers Rename.
- **What revoking does.** If THIS phone is revoked, then after the 6-digit code (or a backup code used instead of it) is accepted, `TotpVerifyActivity` asks for one more unused backup code before the biometric step. It reuses `BackupRecoveryActivity` with the extra `EXTRA_REVOKED_DEVICE`, which hides the recovery choices. Wrong codes count toward the same 3-strike lockout; backing out ends the login. A phone that was never trusted is not "revoked" and logs in normally.
- **A safety check.** Revoking the phone in your hand needs at least one unused backup code, otherwise nobody could log in on it again, so the app refuses and says "Create backup codes first". The revoke dialog for this phone also warns that every login will use up one backup code.

**Likely examiner questions**

1. *How does the app know which row in the list is this phone, if only a name is stored?* It does not use the name. When the phone is trusted, the new row's id is remembered in SharedPreferences for that user. Looking up that id gives this phone's row, so a rename cannot break it, and another account on the same phone has its own entry.
2. *How does a context menu differ from the options menu, and how do you know which row was pressed?* The options menu belongs to the whole screen (the toolbar); a context menu belongs to one view and opens on a long-press after `registerForContextMenu`. Android passes an `AdapterContextMenuInfo` whose `position` is the row; we use it to find the device in the list we are showing.
3. *Why not just delete a device instead of setting `revoked = 1`?* A revoked device must still be remembered: the login checks that THIS phone is on the list and revoked, and then asks for the extra backup code. If the row were deleted, the phone would look like one that was never trusted and would log in normally. The row also keeps the history visible to the user.

## Phase 13

- **Two ways to get a photo, both through other apps.** "Take photo" starts the phone's own camera app with an implicit Intent (`MediaStore.ACTION_IMAGE_CAPTURE`, wrapped by `ActivityResultContracts.TakePicture`). "Choose from gallery" opens the system photo picker (`ActivityResultContracts.PickVisualMedia`). Our app never touches the camera hardware, and the picker needs no storage permission because Android gives us a Uri to just the one picture the user chose.
- **How the camera gets a place to write.** We cannot hand another app a plain file path, so we give it a `content://` Uri made by `FileProvider` for a file in `cache/camera/` (added to `file_paths.xml`). If the user cancels, the empty file is deleted; if a picture was taken it is copied and then the temporary file is deleted. The file name is kept in the saved instance state so a rotation while the camera is open does not lose it.
- **The camera permission.** The QR library already declares `CAMERA`, so the app has it in its manifest; Android then refuses to start the camera app until the permission is granted (we saw `Permission Denial ... revoked permission android.permission.CAMERA` in logcat). So before the camera starts we show our own explanation, then the system dialog; "Not now" or "Don't allow" shows a message pointing to the gallery. Phones without a camera simply do not get the "Take photo" choice.
- **What we store.** `AvatarStore` copies the picture into private storage (`files/avatars/`), turns it upright using the EXIF orientation tag (phones record "rotate 90" in a tag instead of rotating the pixels), cuts the biggest centred square, shrinks it to at most 512 px (decoding only a fraction of the pixels first with `inSampleSize`, so a 12-megapixel photo cannot fill the memory) and saves a JPEG of a few dozen KB. The path goes in `users.avatar_uri`; the old file is deleted; every save uses a new file name so no screen shows a cached old picture.
- **Showing it.** `ProfileActivity` shows it in a `ShapeableImageView` with a "full corner" shape (a circle), next to the username, member-since date and issuer. The Dashboard toolbar shows a small round copy (a `RoundedBitmapDrawable`) that opens the profile when tapped. Files outside our avatar folder are never read or deleted, even if the stored path is damaged.

**Likely examiner questions**

1. *What is an implicit Intent, and how is the camera one different from the explicit Intents elsewhere in the app?* An explicit Intent names the exact Activity (`new Intent(this, LoginActivity.class)`). An implicit one only names an action (`ACTION_IMAGE_CAPTURE`) and Android finds an app that can do it, so any camera app can answer. If none exists we get an `ActivityNotFoundException`, which we catch and report.
2. *Why do you use FileProvider instead of passing `Uri.fromFile`?* Since Android 7 giving another app a `file://` path throws `FileUriExposedException`: a path to our private storage is useless and unsafe for them. FileProvider makes a `content://` Uri and lets that one app read or write that one file for that one request, and only folders listed in `file_paths.xml` can be shared.
3. *Why shrink and crop the photo before saving it?* A phone picture is several megabytes; storing it as-is would waste space and memory (a 4000x3000 bitmap needs about 48 MB when decoded). The avatar is shown as a small circle, so a 512 px centred square is enough and takes a few dozen KB. Reading the EXIF tag first matters because the camera often stores the image sideways and relies on the viewer to turn it.

## Phase 14

- **Settings are saved in SharedPreferences.** SharedPreferences is a small key-value file inside the app's private storage. `AppSettings` owns the key names (`totp_digits`, `totp_period`, `totp_algo`, `auto_lock_ms`, `record_location`) and the allowed values, and every getter checks what it reads: a damaged value falls back to the default, so a bad file can never reach the TOTP engine or the session timer. Every change is saved the moment it is made.
- **The three Spinners (digits 6/8, period 30/60 s, algorithm SHA-1/SHA-256) only affect the NEXT enrollment.** The secret already shared with the authenticator app was made with the old values, so changing them would make the two sides disagree. A red note appears when any choice is not the Google Authenticator default (6 digits, 30 s, SHA-1), and "Set up authenticator again" opens Enroll, which now reads these settings for the QR link, the number of digits it asks for, and the saved account.
- **Time picker.** The auto-lock time uses a `TimePickerDialog` in 24-hour mode. It offers only hours and minutes (hours go up to 23), so "minutes:seconds up to 30 minutes" does not fit it; it is used as hours:minutes, 0:01 to 0:30, and anything else is refused and the picker opens again. The new time is used when the next session is created at login.
- **Help is a WebView with safety limits.** One button loads `assets/help.html` (a page that ships inside the app: plain HTML and CSS, so it works offline and needs no JavaScript), the other loads the RFC 6238 page over https (the only reason for the INTERNET permission). A `WebViewClient` keeps links inside the WebView and only lets two places open (our asset pages and datatracker.ietf.org); JavaScript and file access are off; a `WebChromeClient` drives the progress bar; Back walks back through the WebView's history before it closes the screen.
- **Two broadcast receivers, registered in code.** `BaseActivity` registers them in `onStart` and removes them in `onStop`. `AirplaneModeReceiver` shows a Snackbar "Offline: TOTP still works - it only needs the clock" when airplane mode turns on. `ScreenOffReceiver` locks a protected screen when the screen turns off: the session is ended (memory and database), an `AUTO_LOCK` audit row is written and Login opens. `ACTION_SCREEN_OFF` can only reach receivers registered in code, which is why this is not in the manifest. Both are registered with `RECEIVER_NOT_EXPORTED`, which Android 14 requires you to state.

**Likely examiner questions**

1. *Why can't you declare the screen-off receiver in AndroidManifest.xml?* Since Android 8 most implicit broadcasts cannot wake an app through a manifest receiver, and `ACTION_SCREEN_OFF` was always restricted to receivers registered at run time with `registerReceiver`. So we register in `onStart` and unregister in `onStop`; a receiver that is never unregistered would leak the Activity.
2. *What does RECEIVER_NOT_EXPORTED mean and why is it there?* Since Android 14 an app must say whether other apps may send broadcasts to a receiver registered in code. Our two broadcasts come from Android itself, and "not exported" means no other app can send fake ones (for example a fake "screen off" to log you out). System broadcasts are still delivered.
3. *Why can the WebView not just open any link?* A WebView is a browser inside your app: a page that can open other pages, run scripts or read local files could attack the app. We switch JavaScript and file access off, load only our own asset page and the IETF site, and `shouldOverrideUrlLoading` returns true (blocked, with a message) for every other address; `HelpPagesTest` checks tricks such as `https://datatracker.ietf.org.evil.example/`.

## Phase 15

- **R8 and resource shrinking for the release build.** `release` now has R8 on (`optimization { enable = true }`) and `isShrinkResources = true`. R8 removes unused code, renames what is left and optimises it; the resource shrinker removes unused layouts, strings and images. The release APK is 2.2 MB against 9.8 MB for debug. Because renaming and removing can break code that is reached by reflection, the shrunk build was installed and used: registration, the Enroll screen with its QR image, enrollment with a code computed by an independent program, Keystore encrypt and decrypt, login, and the system fingerprint prompt all worked. R8 reported no missing rules, so `rules.keep` needs no extra lines.
- **FLAG_SECURE on the screens that show codes or secrets** (Dashboard, Enroll, Backup codes). `BaseActivity` asks each screen `isSecureScreen()` and sets `WindowManager.LayoutParams.FLAG_SECURE`. That blocks screenshots and screen recording of the window and blanks its preview in the recent-apps list. A dialog is a separate window, so the one-time backup-codes dialog gets the flag too. On the emulator a screenshot of the Enroll screen comes out completely black.
- **Backup is off.** `allowBackup="false"` and both rule files exclude everything. The TOTP secrets are encrypted with a Keystore key that never leaves the phone, so a restored database could not be decrypted anyway, and the privacy policy promises that nothing leaves the device.
- **A real launcher icon.** The green template icon is replaced by an adaptive icon built from vector drawables: a navy background layer, a foreground with a shield and a key inside the 66 dp safe zone (the part no launcher shape ever crops) and a one-colour layer for Android 13 themed icons. The old bitmap icons were deleted because minSdk 26 always uses the adaptive one.
- **Lint and the release paperwork.** Android Lint now reports 0 errors (it found a stray byte-order-mark character in `Csv.java`; it is now written as `\uFEFF`) and the remaining warnings are only "a newer version exists". Hard-coded English left in Java (durations, a separator, "1 entries") moved to string resources and plurals. `docs/privacy-policy.md`, `docs/play-data-safety.md` and `docs/RELEASE.md` explain the data handling, the Play forms and how to create the signing key and a signed `.aab`; signing details are read from a git-ignored `keystore.properties`.

**Likely examiner questions**

1. *What does R8 do, and why must you test the release build separately from the debug build?* R8 shrinks (removes unused code), obfuscates (renames classes and methods) and optimises. Debug builds skip it. Code that is reached by name at run time (reflection, for example creating a ViewModel) can break after renaming unless a keep rule protects it, so the only proof is running the shrunk app. Libraries ship their own keep rules, which is why none of ours are needed.
2. *How does FLAG_SECURE protect the user, and what does it not protect against?* It tells Android never to copy the window's pixels into screenshots, screen recordings or the recent-apps thumbnail, so a code cannot leak that way, for example through a screen-sharing app. It does not stop someone looking at the screen, a camera pointed at it, or malware that already controls the phone.
3. *Why is the signing key not in the repository, and what happens if it is lost?* Whoever has the key can publish updates that Android accepts as yours, so it must stay private: it is read from a git-ignored `keystore.properties`. If it is lost you can no longer update the app under the same identity, unless you enrolled in Play App Signing, where Google holds the real signing key and you only hold an upload key that can be reset.

## Phase 16

- **The review.** The whole code base was checked against the eight hard rules of the plan and against the login handshake, and the findings are in `docs/SECURITY_REVIEW.md`. The mechanical rules are now enforced by `ProjectRulesTest`, which reads the source: no Kotlin or Compose, only the allowed libraries, no OTP or Base32 library, only `SecureRandom`, no `startActivityForResult`, nothing logged, the TOTP secret stored only through the Keystore, and every screen listed as either session-protected or handshake-guarded.
- **No bypass from outside.** Only `SplashActivity` is exported. Trying `adb shell am start` on the fingerprint, code, Dashboard and Enroll screens gave "Permission Denial … not exported". Every private screen also checks the session itself, taking the user from the session and never from an Intent, so opening the Dashboard directly sends you to Login.
- **A gap inside the app, now closed.** The code, backup-code, fingerprint and Enroll screens each believed a user id in their Intent, so nothing proved the earlier steps had happened. `LoginHandshake` now remembers in memory how far this login got (password OK, then code OK), for one user at a time, for at most ten minutes. A step opens only if the previous one was marked passed for the same user; going back to Login, a logout or a finished fingerprint screen forgets it. Only the fingerprint step creates a session.
- **Tests.** `LoginHandshakeTest` checks the order and the expiry with an injected clock. `HandshakeGuardTest` starts each guarded screen with the right user id but without the earlier steps and checks that Login shows up, nothing is granted, and that the correct order still works. `BiometricGateActivity` also got an optional switch (`EXTRA_SHOW_PROMPT`) that only tests set, so the real system prompt does not cover the screen under test.
- **Demo and viva material.** `docs/DEMO_SCRIPT.md` is a minute-by-minute five-minute demo with preparation (including how to stage a login more than 100 km away so the warning appears live) and what to do when something goes wrong. `docs/VIVA.md` has five questions with short answers for each of the sixteen modules, with course topic and CO tag. The honest limits (a code can be reused inside its time window, re-enrolling from Settings needs only the live session) are listed rather than hidden.

**Likely examiner questions**

1. *Can I start the Dashboard directly, skipping the login?* Not from outside: only the Splash screen is exported and Android refuses anything else. Not from inside: the Dashboard and every other private screen call `enforceSession()`, which needs the token in memory, an unexpired time and a matching hash in the sessions table, and they read the user from the session. The session is created in one place only, after the fingerprint step succeeds.
2. *The screens are not exported, so why did you add `LoginHandshake`?* Defence in depth. "Not exported" protects against other apps, not against a mistake inside this one: a new button or a bug could open the fingerprint screen with a user id and skip the password and code. The screens now check real state: each step opens only if the previous one was recorded as passed for the same user within ten minutes, and the record is cleared on logout, on returning to Login and when the fingerprint screen finishes.
3. *What is the weakest point that is left?* A TOTP code can be reused inside its time window, because refusing a repeat needs a stored "last accepted step" and would break "enroll and log in straight away" with the same code; and setting up the authenticator again from Settings needs only the live session. Both are documented, with the fix, in `docs/SECURITY_REVIEW.md`.
